01 — The Origin

It started with one WhatsApp message.

A student messaged me. A 2024 passout, BCA + MBA background, trying to break into data analytics. He had learned SQL completely — every concept — by writing it in a notebook by hand. No laptop. No compiler. No one to tell him if he was right or wrong.

"I learn SQL completely, concept I get but practical knowledge I don't have... I just write myself in note itself."
— Student message, May 2026

He wasn't the exception. He was everyone. People who want to learn SQL but have no time for long videos, can't self-evaluate, get stuck on Udemy with no one to answer, and can't justify ₹5,000–7,000 on live classes when they're not even sure SQL is for them.

That message stayed with me. And SQLingo was born from it.

02 — The Problem

No feedback loop. No progress.

The problem isn't access to SQL content — YouTube has thousands of SQL tutorials. The problem is that people consume content without ever practicing it. They finish a course and still don't know if they can actually think in SQL.

Duolingo solved this exact problem for languages. You don't watch French videos — you speak French, get feedback instantly, and come back tomorrow. SQL is also a language. So why isn't there a Duolingo for SQL?

No practice environment No feedback loop No affordable option No self-evaluation
03 — The User

Not just freshers. Everyone.

SQLingo targets two equally important users — and this was a deliberate product decision.

1
The fresher
2024/2025 graduate building a data analytics resume. Learning SQL from YouTube, often without a laptop or structured practice. Needs to prove skill before getting the job.
2
The working professional
Already employed, wants to pull their own data without depending on the tech team. Can't commit to a full course. Needs bite-sized, practical learning that fits into a busy schedule.

Both chose SQL for the same reason — it's the least intimidating technical skill. No complex syntax, no environment setup. You write a question, the database answers. SQL is the entry point into data for people who don't see themselves as coders.

04 — Key Product Decisions

Every choice had a reason.

1
No free-type SQL in lessons
The hardest technical problem in SQL learning apps is validating free-form queries — SELECT * FROM users WHERE age > 25 and SELECT * FROM users WHERE 25 < age are both correct. Instead, users learn through select, match, drag, and fill activities. The app always knows the correct answer. No ambiguity, instant validation, zero complexity.
2
Warm teal — not Duolingo green
Colour was chosen for three reasons — accessibility (safe for colour blindness and photosensitive users), education psychology (blue-teal family signals trust and focus), and acquisition neutrality (no major edtech brand owns this exact tone). Every colour decision was documented before a line of code was written.
3
No mascot
Duolingo's owl drives retention through emotional guilt. But a mascot creates brand dependency — any acquiring company would inherit it. SQLingo uses a clean wordmark instead. Acquisition-friendly from day one.
4
Freemium — free lessons, paid mock interviews
Free tier lowers the entry barrier completely — no credit card, no commitment. The natural upgrade trigger is job readiness — once someone finishes free lessons and feels confident, they want to prove it. That's when they pay for AI-powered SQL mock interviews. The student who couldn't afford ₹7,000 for live classes can now access real value for free, and upgrade when it matters.
5
Mistake retry — Duolingo's core mechanic
If a user gets a question wrong, it's added to a queue. After all lesson questions are complete, only the wrong ones come back — one by one — until the user gets them right. This is overlearning. The concept has to become automatic, not just recognised.
6
Sakila database — real, not invented
Every lesson uses Sakila — an open-source MySQL practice database (BSD license, free to use). Real database, real table names, real column names. Students learn SQL on actual data structures — not fictional examples that don't translate to the real world. The DVD rental store context also makes it human — before Netflix, this was how people watched movies.
05 — How It Was Built

No developer. No budget. Just process.

SQLingo was built entirely through a structured PM process — discovery, design decisions, content creation, and iterative testing. The technical build used AI-assisted development with zero developer dependency.

Day 1
Discovery & Problem Definition
Student message → problem statement → user personas → competitor analysis. Documented before any design or build started.
Day 1
Developer Questionnaire
Completed a full product discovery questionnaire — platform scope, gamification, learning content, AI features, monetisation, timeline, and budget. Every answer had reasoning behind it.
Day 1
Design System Decisions
Colour (warm teal #0D9488), font (Nunito + JetBrains Mono), logo (clean wordmark), voice and tone — all decided with documented rationale before building.
Day 1
Content Architecture
Lesson structure designed from 6 years of SQL training experience — 3 modules, 6 lessons per module, 8+ activities per lesson. Same concept taught from multiple angles until it's muscle memory.
Day 1
Build, Test, Iterate
Module 1 built and tested. 6 observations collected during testing. All corrections applied — content rewritten, wrong question fixed, mistake retry logic rebuilt from scratch.
Day 1
Deployed — Test & Production
Two separate environments set up on Vercel. Test environment for changes, production for users. Both live and working on day one.

07 — What I Learned

The PM lessons behind the product.

🎯
User insight beats market research
The best product insight came from one WhatsApp message — not a survey or competitor analysis. Real users tell you everything.
⚙️
Solve the hardest technical problem first
Free-type SQL validation was the biggest technical risk. Solving it early — through structured activities — shaped the entire product architecture.
🎨
Design decisions need documentation
Every colour, font, and layout choice was documented with reasoning. This is what separates a PM portfolio from a developer portfolio.
🔁
Test with real users, not assumptions
6 corrections came from one round of testing. No amount of planning replaces actually using the product and observing what breaks.
💰
Budget is not the constraint
SQLingo was built with zero budget. Process, clarity, and domain expertise replaced money. A working product in one day.
🚀
Launch before you're ready
Module 1 is live while Modules 2 and 3 are still being built. Real users on a real product beats a perfect product no one has seen.
