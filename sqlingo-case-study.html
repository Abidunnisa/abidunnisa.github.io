01 — The Origin

It started with one WhatsApp message.

A student messaged me. A 2024 passout, BCA + MBA background, trying to break into data analytics. He had learned SQL completely — every concept — by writing it in a notebook by hand. No laptop. No compiler. No one to tell him if he was right or wrong.

"I learn SQL completely, concept I get but practical knowledge I don't have... I just write myself in note itself."
— Student message, May 2026

He wasn't the exception. He was everyone. People who want to learn SQL but have no time for long videos, can't self-evaluate, get stuck on Udemy with no one to answer, and can't justify ₹5,000–7,000 on live classes when they're not even sure SQL is for them.

That message stayed with me. And SQLingo was born from it.

02 — The Problem

No feedback loop. No progress.

The problem isn't access to SQL content — YouTube has thousands of SQL tutorials. The problem is that people consume content without ever practicing it. They finish a course and still don't know if they can actually think in SQL.

Duolingo solved this exact problem for languages. You don't watch French videos — you speak French, get feedback instantly, and come back tomorrow. SQL is also a language. So why isn't there a Duolingo for SQL?

No practice environment No feedback loop No affordable option No self-evaluation
03 — The User

Not just freshers. Everyone.

SQLingo targets two equally important users — and this was a deliberate product decision.

1
The fresher
2024/2025 graduate building a data analytics resume. Learning SQL from YouTube, often without a laptop or structured practice. Needs to prove skill before getting the job.
2
The working professional
Already employed, wants to pull their own data without depending on the tech team. Can't commit to a full course. Needs bite-sized, practical learning that fits into a busy schedule.

Both chose SQL for the same reason — it's the least intimidating technical skill. No complex syntax, no environment setup. You write a question, the database answers. SQL is the entry point into data for people who don't see themselves as coders.

04 — Key Product Decisions

Every choice had a reason.

1
No free-type SQL in lessons
The hardest technical problem in SQL learning apps is validating free-form queries — SELECT * FROM users WHERE age > 25 and SELECT * FROM users WHERE 25 < age are both correct. Instead, users learn through select, match, drag, and fill activities. The app always knows the correct answer. No ambiguity, instant validation, zero complexity.
2
Warm teal — not Duolingo green
Colour was chosen for three reasons — accessibility (safe for colour blindness and photosensitive users), education psychology (blue-teal family signals trust and focus), and acquisition neutrality (no major edtech brand owns this exact tone). Every colour decision was documented before a line of code was written.
3
No mascot
Duolingo's owl drives retention through emotional guilt. But a mascot creates brand dependency — any acquiring company would inherit it. SQLingo uses a clean wordmark instead. Acquisition-friendly from day one.
4
Freemium — free lessons, paid mock interviews
Free tier lowers the entry barrier completely — no credit card, no commitment. The natural upgrade trigger is job readiness — once someone finishes free lessons and feels confident, they want to prove it. That's when they pay for AI-powered SQL mock interviews. The student who couldn't afford ₹7,000 for live classes can now access real value for free, and upgrade when it matters.
5
Mistake retry — Duolingo's core mechanic
If a user gets a question wrong, it's added to a queue. After all lesson questions are complete, only the wrong ones come back — one by one — until the user gets them right. This is overlearning. The concept has to become automatic, not just recognised.
6
Sakila database — real, not invented
Every lesson uses Sakila — an open-source MySQL practice database (BSD license, free to use). Real database, real table names, real column names. Students learn SQL on actual data structures — not fictional examples that don't translate to the real world. The DVD rental store context also makes it human — before Netflix, this was how people watched movies.
05 — How It Was Built

No developer. No budget. Just process.

SQLingo was built entirely through a structured PM process — discovery, design decisions, content creation, and iterative testing. The technical build used AI-assisted development with zero developer dependency.

Day 1
Discovery & Problem Definition
Student message → problem statement → user personas → competitor analysis. Documented before any design or build started.
Day 1
Developer Questionnaire
Completed a full product discovery questionnaire — platform scope, gamification, learning content, AI features, monetisation, timeline, and budget. Every answer had reasoning behind it.
Day 1
Design System Decisions
Colour (warm teal #0D9488), font (Nunito + JetBrains Mono), logo (clean wordmark), voice and tone — all decided with documented rationale before building.
Day 1
Content Architecture
Lesson structure designed from 6 years of SQL training experience — 3 modules, 6 lessons per module, 8+ activities per lesson. Same concept taught from multiple angles until it's muscle memory.
Day 1

Day 1

Two separate environments set up on Vercel. Test environment for changes, production for users. Both live and working on day one.
05b — Module 2 Build

WHERE & Operators — what it took.

Module 2 was the first real test of the SQLingo content framework. 6 lessons, 48 activities, covering every type of SQL operator — comparison, arithmetic, logical, special, and NULL handling.

The teaching anchor: WHERE was introduced using Amazon's filter system — something every user already understands. Single filter = one WHERE condition. Multiple filters = AND, OR. The mental model transferred instantly.

What testing found: Real testing caught issues that no amount of planning would have — a mathematically ambiguous question where two options were both correct, a MySQL division result that contradicted the explanation, and a JavaScript syntax error from apostrophes inside drag-and-drop word banks breaking the entire activity.

1
Ambiguous arithmetic question
A question asked which query doubled the rental rate. Two options were correct — rental_rate * 2 and rental_rate + rental_rate. Fixed by replacing one option with rental_rate + 2, which adds 2 instead of doubling. One unambiguous correct answer.
2
MySQL division behaviour
The question stated SELECT 10/3 returns 3 (integer division). A real MySQL test proved it returns 3.3333. The explanation and correct answer were both wrong. Fixed to reflect actual MySQL behaviour — an important distinction for learners.
3
Drag activity syntax error
Drag-and-drop words containing SQL strings like rating = 'G' used apostrophes that broke the JavaScript when placed inside single-quoted JS strings. Fixed by converting those specific activities to multiple choice — same concept tested, no technical fragility.
4
Technically correct wrong answer
An IN operator question had option 1 as WHERE rating = 'G' OR rating = 'PG' OR rating = 'PG-13' — valid SQL, just verbose. Students could reasonably choose it. Fixed by replacing it with WHERE rating = 'G', 'PG', 'PG-13' — which looks plausible but is invalid SQL syntax.

The PM lesson: Content quality in a learning app is not just about accuracy — it is about unambiguity. Every question must have exactly one defensible correct answer. Testing with a real user (the trainer herself) caught all four issues before a single student saw them.

06b — Technical Architecture

What it is actually built with.

SQLingo is a single HTML file. No framework. No backend. No database. Everything — HTML structure, CSS styling, and JavaScript logic — lives in one file deployed on GitHub Pages and Vercel.

1
HTML + CSS + JavaScript
The entire app — all lessons, all activities, all gamification logic, mistake retry queue, XP tracking — is written in vanilla HTML, CSS, and JavaScript. No React, no Node, no build tools. One file that runs in any browser.
2
GitHub + Vercel
GitHub stores the code. Vercel hosts it live. Every time a file is uploaded to GitHub, Vercel automatically rebuilds and redeploys — no manual steps. Two environments (dev and production) connected to two separate GitHub repositories.
3
localStorage for progress
XP, streak, and lesson completion are saved using the browser's localStorage. This means progress persists across page refreshes on the same device and browser — but does not sync across devices or sessions on different browsers.
4
Google Fonts
Nunito for all UI text — chosen for accessibility (rounded letterforms, dyslexia-friendly). JetBrains Mono for all SQL code — built specifically for code readability. Both loaded from Google Fonts CDN, free.
05c — Module 3 Build

ORDER BY & LIMIT — sort and control.

Module 3 covered sorting and limiting results. 4 lessons, 32 activities. Simpler than Module 2 conceptually — but testing still caught two issues before a single student saw them.

1
Identical options in a multiple choice question
A question asking for the 10 shortest films had two options that were functionally identical — ORDER BY length and ORDER BY length ASC are the same thing since ASC is the default. Fixed by replacing one with ORDER BY length DESC — which gives the longest films, making it a clearly wrong answer.
2
Function used before it was taught
A question used LENGTH() — a string function — inside an ORDER BY clause. LENGTH() is not taught until Module 6. Using it in Module 3 assumes knowledge students do not have yet. Replaced with a question using only concepts from Modules 1 to 3.

The PM lesson: Content sequencing is a product decision. Every concept used in a question must have been taught before that question appears. Curriculum mapping is not just about what to teach — it is about what order to teach it in.

05d — Latest Updates

What shipped this week.

Four updates shipped based on real testing — one from a bug found internally, two from product decisions, and one from direct user feedback from a complete SQL beginner.

1
Bug fix — multiple correct answers in fill questions
A fill-in-the-blank question asked for the not-equal operator. The answer was set to != only — but SQL also accepts <> for the same thing. A real user typed <> and got marked wrong. Fixed by updating the answer validation logic to accept an array of correct answers. Now any fill question can have multiple valid answers.
2
Module test — 20 questions, no hints, 80% pass mark
After completing all lessons in a module, a test button unlocks. 20 random questions drawn from across all lessons. No hints, no feedback during the test, one chance per question. Pass at 80% to earn a bonus 100 XP and mark the module complete. Fail — wrong answers are shown and the test can be retaken with a reshuffled question set. Same philosophy as Duolingo — completion is not enough, you have to prove it.
3
ⓘ Info button — quick reference on every activity
A small info button on every activity card opens a quick reference panel — the key syntax for that lesson, not the answer to the question. Requested by a real user who found BETWEEN, LIKE, and the % wildcard tricky without a reference. The panel shows only the template — enough to jog memory without giving anything away.
4
First external user feedback
A complete SQL beginner tested the app and provided three pieces of feedback — BETWEEN and LIKE feel tricky and need more practice questions, the % wildcard needed a reference option, and the <> operator being rejected as wrong was confusing. All three were actioned. Real user feedback in day 3 of building — before a single line of marketing.

The PM lesson: The best product decisions come from watching real users struggle — not from assumptions. Every one of these updates came from someone actually using the product, not from a planning session.

06 — Live Product

It's live.

Modules 1, 2, and 3 are live and working — 13 lessons, 105 activities, mistake retry, XP system, streak tracking. Free to use, no sign-up required.

Current limitations: SQLingo is currently a single-file frontend with no backend or database. Progress is saved in the browser's localStorage — it persists on the same device but does not sync across devices or browsers. User login, leaderboards, and cross-device progress are not yet built. Phase 1 backend work — connecting a database and user authentication — is the identified next milestone.

07 — What I Learned

The PM lessons behind the product.

🎯
User insight beats market research
The best product insight came from one WhatsApp message — not a survey or competitor analysis. Real users tell you everything.
⚙️
Solve the hardest technical problem first
Free-type SQL validation was the biggest technical risk. Solving it early — through structured activities — shaped the entire product architecture.
🎨
Design decisions need documentation
Every colour, font, and layout choice was documented with reasoning. This is what separates a PM portfolio from a developer portfolio.
🔁
Test with real users, not assumptions
6 corrections came from one round of testing. No amount of planning replaces actually using the product and observing what breaks.
💰
Budget is not the constraint
SQLingo was built with zero budget. Process, clarity, and domain expertise replaced money. A working product in one day.
🚀
Launch before you're ready
Module 1 is live while Modules 2 and 3 are still being built. Real users on a real product beats a perfect product no one has seen.
